# Baseline 与提分教程适配分析

## 1. 文档目的与适用范围

本文基于以下两份 PDF 文档进行整理与分析：

- `baseline`：`定稿版【跑通Baseline】赛题四：金融长文本Agent的动态记忆压缩与高效问答挑战.pdf`
- `提分教程`：`定稿版【提分教程】赛题四：金融长文本Agent的动态记忆压缩与高效问答挑战.pdf`

本文目标不是复述竞赛方案本身，而是结合当前项目的实际约束，筛选可复用、可落地、可分阶段引入的技术路线。当前项目的现实边界如下：

- 项目仍处于 MVP 到联调优化阶段，现有能力以 `FastAPI + React` 骨架、预处理、规则召回、证据筛选和逐选项推理为主，尚未进入复杂 Agent 编排阶段。
- 当前检索主链路已经明确采用“内存版 BM25 + 结构化过滤 + 规则加权”，并且明确不允许使用向量模型。
- 项目近期暴露出的首要瓶颈不是“大模型推理不够强”，而是预处理质量、文档解析质量、分块完整性和检索召回质量。

因此，本文所有适配判断均遵循三个原则：

- 先修基础链路，再引入复杂架构。
- 优先离线、确定性、可测试的增强手段。
- 对不满足当前约束的方案，仅保留“方法论参考”，不作为当前主线实现。

## 2. PDF 内容核心梳理

### 2.1 Baseline 文档核心内容

#### 2.1.1 赛题目标、约束与优化方向

- 赛题是金融长文档问答，重点能力不是单纯抽取，而是“信息定位 + 知识理解 + 推理计算”的组合能力，尤其涉及跨文档对比、公式计算、条款定位和逻辑判断。[来源：baseline p1-p3]
- 评分机制中准确率权重高于 Token 效率，意味着系统优化顺序应当是“先提高答对率，再控制消耗”。[来源：baseline p1]
- A 榜题目给定 `doc_ids`，这意味着问题本质上更接近“限定文档集内的证据定位与推理”，而不是开放域检索。[来源：baseline p1]
- baseline 明确反对一开始就引入复杂框架或复杂检索，认为在基础链路未稳定前，检索切片会破坏上下文连贯性，并可能在粗排质量不足时导致降分。[来源：baseline p5-p6]

#### 2.1.2 Baseline 的工程定位

- baseline 方案是最小可运行基线，核心方法是“硬截断 + 单轮 LLM 调用 + no-tool”，其目标是快速跑通可提交结果，而非追求高分。[来源：baseline p4]
- baseline 采用每篇文档截断、拼接 prompt、单轮回答、答案规范化的方式，以最小工程复杂度保证端到端可用。[来源：baseline p4, p14-p19]
- baseline 选择 `no-tool` 而非 Function Calling，核心原因是 FC 带来的工具 schema、二阶段交互和中间状态会显著提高 prompt token 消耗。[来源：baseline p7]
- baseline 保留了回退模型和重试机制，体现出“先保证流程稳定，再讨论精度优化”的工程思路。[来源：baseline p17-p18]

#### 2.1.3 Baseline 对后续优化的明确判断

- baseline 已经把优化重点清晰指向五个方向：PDF 解析质量、检索策略、证据聚合、答案约束、领域知识增强。[来源：baseline p21]
- baseline 特别强调 PDF 解析是上游第一瓶颈；若表格、数字、段落顺序和标题层级在解析阶段出错，后续检索和推理都建立在错误输入上。[来源：baseline p22]
- 对上下文管理，baseline 认为固定截断是粗放策略，后续应升级到切片检索、片段组装、动态上下文长度控制。[来源：baseline p23]
- 对推理流程，baseline 建议从单轮回答升级到迭代检索、自我纠错、多选逐项验证和证据一致性校验。[来源：baseline p24]
- 对知识组织，baseline 建议将高价值字段做结构化抽取，用于跨文档比较和计算题处理。[来源：baseline p25]

### 2.2 提分教程文档核心内容

#### 2.2.1 题型拆解与系统能力映射

- 提分教程将题目拆为公式计算、跨文档对比、多文档联合推理、条款定位、事实查找五类，并指出很多题实际上是多能力叠加题。[来源：提分教程 p1-p4]
- 文档强调两个基础问题必须同时解决：一是所有相关文档都要被读到，二是关键证据必须被精确定位。[来源：提分教程 p3]
- 这一拆解实质上要求系统从“统一策略”升级为“按题型分配检索、上下文和推理策略”的体系。[来源：提分教程 p1-p4, p19]

#### 2.2.2 PDF 解析路线

- 提分教程系统比较了 `PyMuPDF4LLM`、`Marker`、`MinerU`、`olmOCR` 等 PDF 解析路线，并给出按硬件环境分层选型的建议。[来源：提分教程 p7-p11]
- 文档认为 PDF 解析是整个 RAG/Agent 链路的第一步且最重要的一步，原因是后续所有步骤都依赖解析后的文本质量。[来源：提分教程 p7]
- 提分教程提出的预处理补强包括：页眉页脚过滤、表格后处理、公式补标注、段落合并、结构路径标注。[来源：提分教程 p11]

#### 2.2.3 RAG 检索优化路线

- 提分教程将 RAG 优化拆为分块、混合检索、重排序、查询增强、片段组装、前沿 RAG 范式等层次。[来源：提分教程 p12-p24]
- 在分块上，文档从固定切块、滑动窗口、语义分块进一步延伸到多粒度 `parent-child` 思路，强调“检索用小块、回答用大块”。[来源：提分教程 p12]
- 在检索上，文档推荐 `BM25 + 向量检索 + HyDE + Rerank` 作为通用强方案，但也明确说明 embedding 和 rerank 在正式提交中不可用，相关内容更多是完整技术栈的扩展学习。[来源：提分教程 p12-p16]
- 在高阶范式上，文档介绍了 `GraphRAG`、`LightRAG`、`StructRAG`、`RAPTOR`、`Self-RAG`、`CRAG`、`KAG`、多跳 RAG、Agentic RAG 等路径，并分别说明其解决的是扁平检索、全局理解、质量评估、领域知识对齐等问题。[来源：提分教程 p17-p24]
- 文档给出了一个十阶段渐进路线，从 `BM25 + 语义分块` 一直推进到 `smolagents Code Agent`，强调每一步都要做实际提交验证，避免“加复杂度但不涨分”。[来源：提分教程 p24]

#### 2.2.4 动态记忆压缩与上下文管理

- 提分教程明确指出“动态记忆压缩”是赛题名中的核心挑战，本质是如何在固定 Token 预算下保留最有价值的信息。[来源：提分教程 p25]
- 文档从动态截断、信息密度控制进一步上升到分层记忆管理，系统引用了 `Kimi Context Compaction`、`Hermes trajectory compressor`、`Claude Code` 四层压缩、`Codex Memento`、`generic-agent` 的 L1-L4 分层记忆、`MemGPT` 等实践。[来源：提分教程 p26-p34]
- 这些方案的共识是：压缩不能只做“通用摘要”，必须保护题目原文、精确数值、公式、例外条款和最新推理状态；中间阅读过程可以被结构化摘要替代。[来源：提分教程 p26-p34]
- 提分教程给出了适合单题推理的摘要模板，强调摘要应当包含目标、已读文档、关键公式、数值、待验证点，而不是自由文本式总结。[来源：提分教程 p34]

#### 2.2.5 答案验证、Agent 化与工具执行

- 提分教程建议在 baseline 单轮回答外增加自检机制，并总结了否定词遗漏、年份混淆、条件遗漏、跨文档混淆等常见错误模式。[来源：提分教程 p35]
- 在 Prompt 工程上，文档主张按题型差异化设计提示模板，而不是使用单一模板处理全部问题。[来源：提分教程 p35]
- 在 Agent 化方向上，文档认为 Function Calling 虽然更耗 Token，但在补搜、跨文档逐份搜索、信息不足再检索等场景具备价值。[来源：提分教程 p36]
- 对计算题，文档明确提出“不要让 LLM 直接算，而是让 LLM 写 Python 代码并通过 Bash/执行器计算”的策略，以消除多步算术错误。[来源：提分教程 p36-p39]
- `smolagents` 被介绍为更轻量的 Code Agent 范式，其核心价值是通过 Python 代码一次性组织多个工具调用、中间变量和条件逻辑，减少 JSON tool calling 的序列化开销和推理步数。[来源：提分教程 p40-p43]

## 3. 可复用思路与技术的适配分析

### 3.1 高适配、应直接纳入当前主线的内容

#### 3.1.1 PDF 解析质量优先于下游花式优化

适配结论：`强适配，且应作为当前第一优先级。`

原因如下：

- baseline 与提分教程都把 PDF 解析质量定位为整个系统上限的前置条件，这与当前项目已暴露出的预处理断链、单文件解析异常、文档与 chunks 失配问题高度一致。[来源：baseline p21-p22；提分教程 p7-p11]
- 当前项目近期实际问题已经证明：如果 PDF 解析或预处理阶段不稳定，下游检索参数再怎么调也只能在错误数据上优化。
- 当前项目又处于“禁止向量”的约束下，更依赖显式结构质量；这意味着标题层级、条款号、章节路径、表格结构、数字保真度比一般 RAG 项目更重要。

建议落地方式：

- 继续把预处理稳定性、解析质量校验和异常文档隔离作为主线工程任务。
- 在现有 `PyMuPDF`/文本解析基础上补充解析后校验，而不是一开始重构整个解析框架。
- 对高风险文档类型优先做结构增强：财报表格、保险条款公式、监管条款号、合同章节路径。

#### 3.1.2 题型分流与差异化策略

适配结论：`强适配，应尽快纳入在线链路。`

原因如下：

- 提分教程的题型划分非常符合当前项目数据特征，且与现有五大金融领域天然对应。[来源：提分教程 p1-p4]
- 当前项目若继续对所有问题套同一检索和推理模板，会持续损失公式计算题、多文档对比题和多选题的精度。
- 题型分流不依赖向量模型，也不要求引入重型框架，完全符合当前技术栈约束。

建议落地方式：

- 在任务规划阶段增加题型识别标签，如“计算题 / 条款定位题 / 对比题 / 事实查找题 / 多选高风险题”。
- 将题型标签直接接入现有检索 plan，控制 `query rewrite`、候选文档数、chunk 组装方式和答案验证策略。
- 对多选题启用逐选项验证；对计算题启用数值提取和公式校验；对条款题提高条款号、章节路径的权重。

#### 3.1.3 语义分块、滑动窗口与结构路径增强

适配结论：`强适配，是当前 BM25 体系最现实的提分手段。`

原因如下：

- 提分教程虽然在完整技术栈中介绍了向量与 rerank，但其对“语义分块 + 滑动窗口 + 结构路径”的论述本身并不依赖向量模型。[来源：提分教程 p12, p16]
- 当前项目的检索体系本质上依赖显式词项与结构信息，因此优质 chunk 边界和 `section_path` 价值非常高。
- 当前 `retriever.py` 已经对 `title / section_path / clause_no / chunk_text` 做加权，这意味着项目已经具备承接更优分块结果的能力。

建议落地方式：

- 将分块从单纯长度切分升级为“按标题层级/段落边界切分 + 适度 overlap”。
- 对每个 chunk 强制保留 `title`、`section_path`、`clause_no` 等结构字段，并在预处理产物中落盘。
- 对表格和条款类 chunk 使用更小粒度，对研报和财报叙述段使用较大粒度。

#### 3.1.4 CRAG 式的“质量评估 + 自动回退”

适配结论：`强适配，且非常适合当前无向量约束。`

原因如下：

- 提分教程中的 CRAG 思路不是必须联网或必须向量检索，它的关键价值在于“不要盲信检索结果”，而是对检索质量做分级并决定是否回退。[来源：提分教程 p21-p22]
- 当前项目已有稳定的 baseline 式回退思想，且历史上确实存在“检索结果反而比粗暴截断更差”的现实风险。
- 这类机制高度契合当前项目的工程需求：让“增强检索”在有效时增益，在失效时自动退回稳健路径。

建议落地方式：

- 基于轻量规则实现第一版检索质量评估器，例如：问题词覆盖率、数字命中率、条款号命中率、候选片段相互一致性、top1-topk 分差。
- 将检索结果分为 `good / ambiguous / bad` 三档。
- `good` 直接进入推理，`ambiguous` 触发查询改写或扩大候选范围，`bad` 回退到文档前部截断或全文局部扫描。

#### 3.1.5 结构化抽取而非“纯文本反复阅读”

适配结论：`强适配，但应以轻量字段抽取起步。`

原因如下：

- baseline 与提分教程都指出，跨文档比较和计算题最怕每次都让模型重新在原文中找同类字段。[来源：baseline p25；提分教程 p19, p30-p34]
- 当前项目又明确强调显式建模，因此离线抽取“等待期、免责、现金价值、营收、净利润、评级、发行条款”等字段，本质上是对 BM25 的补强，而不是替代。
- 这类结构化结果还能直接接入规则加权与答案验证，复用价值高。

建议落地方式：

- 不直接上知识图谱，先做领域模板化字段抽取。
- 保险域优先抽 `等待期 / 免责 / 退保规则 / 现金价值 / 身故保险金公式`。
- 监管域优先抽 `条款号 / 主体 / 时限 / 条件 / 例外`。
- 财报域优先抽 `营收 / 净利润 / 现金流 / 研发投入 / 年份`。

### 3.2 中高适配、应在主线稳定后分阶段引入的内容

#### 3.2.1 动态记忆压缩的“分层保留”思想

适配结论：`中高适配，但应采用轻量实现，不宜一开始做完整 Agent 记忆系统。`

原因如下：

- 提分教程中引用的 Kimi、Hermes、Claude Code、Codex、generic-agent、MemGPT 等方案，本质共识是“分层保留关键事实，压缩中间过程”。[来源：提分教程 p26-p34]
- 当前项目不是长会话 Agent，而是“长文档 + 短推理”系统，因此无需照搬完整会话压缩框架。
- 但其中“保护精确数值、公式、例外条款原文；压缩中间阅读轨迹”的思想，非常适合当前多文档题与复杂题。

建议落地方式：

- 在单题执行流程中增加中间态对象，而不是增加通用记忆系统。
- 中间态按层保存：题目原文、结构化证据、精确引用片段、推理摘要、最终答案。
- 压缩策略优先采用 `Snip -> 结构化提取 -> 必要时摘要` 的三级策略，而不是每轮都调 LLM 做总结。

#### 3.2.2 自检机制与多轮验证

适配结论：`中高适配，应先在高风险题型上局部开启。`

原因如下：

- 提分教程总结的错误模式与当前项目场景高度吻合，尤其是否定词、年份、条件遗漏、跨文档串文错误。[来源：提分教程 p35]
- 自检机制能显著降低多选题与条款题的低级错误，但如果全量开启，会增加延迟和 token 消耗。

建议落地方式：

- 不全量启用二次推理。
- 只对多选题、计算题、候选答案不稳定题启用二次校验。
- 校验内容聚焦于“证据是否支持答案”，而不是重复生成整段 reasoning。

#### 3.2.3 Bash/Python 计算工具

适配结论：`中高适配，适合在计算题链路中独立引入。`

原因如下：

- 提分教程对计算题的判断非常准确：LLM 文本推理不是精确计算器，让模型写代码并执行是更可靠的路线。[来源：提分教程 p36-p39]
- 当前项目中保险、财报、合同类题目都存在数值比较和公式计算需求。
- 该方案不依赖向量，也不要求完整 Agent 框架，可以作为独立工具能力嵌入现有系统。

建议落地方式：

- 只在明确识别为计算题时触发。
- 上游先完成数值和公式抽取，再把结构化数据交给受限 Python 执行器。
- 执行器必须具备超时、禁用危险模块和固定输入模板，避免把通用终端能力暴露给主链路。

### 3.3 低适配或当前不建议主线引入的内容

#### 3.3.1 向量检索、Embedding、Rerank 主链路

适配结论：`当前不适配，不应进入正式主线。`

原因如下：

- 提分教程虽然在完整 RAG 栈中推荐混合检索和 rerank，但也明确指出 embedding 与 rerank 在正式提交中不允许使用。[来源：提分教程 p13-p16]
- 当前项目已有硬性约束：不得使用向量模型。
- 在当前阶段继续围绕 embedding 设计主架构会直接偏离项目边界。

处理建议：

- 只保留其“为什么有效”的方法论，用于启发当前 BM25 体系的查询改写、多路召回、规则融合和质量评估。
- 不新增任何依赖 embedding 的核心模块。

#### 3.3.2 GraphRAG、LightRAG、RAPTOR 等高阶知识结构方案

适配结论：`当前低适配，可作为中长期研究方向，不宜近期主线投入。`

原因如下：

- 这些方案的目标很先进，适合跨文档全局理解和复杂知识组织，但构建、调试、评估成本都很高。[来源：提分教程 p17-p24]
- 当前项目连基础预处理稳定性、chunk 完整性和 BM25 召回质量都还在修补阶段，过早引入图结构或树结构会放大复杂度。
- 即使选择轻量版 LightRAG，其实体抽取、关系建模和增量维护也会引入新的长尾问题。

处理建议：

- 将其降级为“领域结构化抽取”的远期演进方向。
- 先用 JSON 字段和规则索引替代图数据库式复杂实现。

#### 3.3.3 全量 Agentic RAG 与 smolagents Code Agent 主框架替换

适配结论：`当前低适配，不建议直接替换现有执行主链。`

原因如下：

- baseline 已经指出 FC 相比 no-tool 会带来额外 token 成本；提分教程也承认 Agent 化要以更高复杂度和更多调优为代价。[来源：baseline p7；提分教程 p24, p36-p43]
- 当前项目的主痛点仍是数据质量和检索质量，而不是“缺一个通用 Agent 框架”。
- `smolagents` 的价值主要在复杂多步工具协同，但当前项目更需要的是聚焦型优化，而不是框架层重构。

处理建议：

- 不做主链替换。
- 仅保留“代码执行比 JSON 工具调用更适合复杂计算”的局部思路，在计算题专用链路中吸收。

## 4. 落地实施优先级建议

### 4.1 P0：立即执行

- `P0-1` 预处理与解析质量治理：补齐解析后校验、异常文档隔离、结构字段完整性检查，持续修复 PDF 断链与 chunk 缺失问题。[来源：baseline p21-p22；提分教程 p7-p11]
- `P0-2` 题型识别与检索分流：为问题增加题型标签，并基于题型切换检索参数、候选规模和验证策略。[来源：提分教程 p1-p4, p19]
- `P0-3` 分块升级：从粗粒度切分升级为“结构边界切分 + overlap + section_path 保留”，增强 BM25 可用性。[来源：提分教程 p12]
- `P0-4` 检索质量评估与回退：实现轻量 CRAG 机制，避免低质量检索直接污染答案生成。[来源：baseline p5-p6；提分教程 p21-p22]

### 4.2 P1：主线稳定后推进

- `P1-1` 结构化字段抽取：按领域抽取高价值字段，服务跨文档比较、公式计算和规则加权。[来源：baseline p25；提分教程 p19, p30-p34]
- `P1-2` 高风险题型自检：对多选题、计算题和条款题引入二次校验，重点检查否定词、年份、条件和跨文档混淆。[来源：提分教程 p35]
- `P1-3` 轻量动态压缩：在单题链路中实现“原文保护 + 结构化摘要替代中间阅读过程”的上下文管理策略。[来源：提分教程 p26-p34]
- `P1-4` 计算题 Python 执行器：为公式计算题提供受限代码执行能力，替代 LLM 直接算术。[来源：提分教程 p36-p39]

### 4.3 P2：中长期探索

- `P2-1` 更强 PDF 解析器试点：在资源允许时，针对高风险文档类型评估 `Marker` 或 `MinerU` 的离线补强价值。[来源：提分教程 p7-p11]
- `P2-2` 结构化知识网络演进：在轻量字段抽取稳定后，再评估图结构或树结构知识组织的真实收益。[来源：提分教程 p17-p24]
- `P2-3` 局部 Agent 化：仅在计算题或复杂多跳题上试点 Code Agent，而非替换全链路执行框架。[来源：提分教程 p36-p43]

## 5. 潜在风险与应对方案

### 5.1 风险一：过早引入复杂架构，掩盖基础数据问题

风险说明：

- 当前项目的核心问题仍集中在预处理、解析和召回基础质量。
- 如果此时直接切换到图 RAG、Agentic RAG 或复杂框架，可能导致问题来源更加难以定位。

应对方案：

- 严格采用渐进式实验机制，每次只改一个模块。
- 固定评测集、固定主指标、保留回滚能力。
- 复杂方案必须先在离线 A 榜评测中证明收益，再考虑进入主链。

### 5.2 风险二：动态压缩导致关键条件丢失

风险说明：

- 提分教程已经明确指出，例外条款、精确数值和公式在摘要化过程中极易被误改写或遗漏。[来源：提分教程 p28-p34]
- 当前项目题目中大量错误都可能由“漏掉否定条件或例外条件”触发。

应对方案：

- 规定三类内容禁止摘要化：题目原文、公式/数字原文、例外条件原文。
- 压缩结果必须带来源位置和原文回链。
- 对多选题和条款题优先使用结构化提取而不是自由摘要。

### 5.3 风险三：检索增强后反而降分

风险说明：

- baseline 已给出明确经验：在检索边界、排序和去噪机制不足时，检索方案可能不如稳定的截断方案。[来源：baseline p5-p6]
- 当前项目同样存在 chunk 质量不稳和召回波动问题。

应对方案：

- 检索链路必须配套质量评估器和回退策略。
- 所有检索优化都必须逐步上线，并与 baseline 回退路径并存。
- 评估时不仅看最终准确率，还要看“召回到正确文档/条款的比例”。

### 5.4 风险四：计算工具引入新的执行安全与稳定性问题

风险说明：

- Bash/Python 执行器虽然能提高计算准确性，但会引入代码执行安全、超时、异常恢复和可观测性问题。[来源：提分教程 p39-p42]

应对方案：

- 仅开放白名单内的数学与数据结构能力。
- 默认超时、禁止危险模块、固定输入输出协议。
- 只在计算题专用链路启用，不开放为通用执行环境。

### 5.5 风险五：领域结构化抽取成本高、维护复杂

风险说明：

- 不同领域文档结构差异大，若一开始就做过宽的字段抽取，容易出现模板泛化不足、维护成本高、抽取质量参差不齐的问题。

应对方案：

- 先按领域选最能影响正确率的 3-5 个核心字段。
- 采用模板化、小步迭代的字段设计，不追求一次性覆盖所有知识。
- 抽取产物必须可验证、可追溯，并与原文建立明确映射。

## 6. 综合结论

- 两份 PDF 的共识非常清晰：真正的提分不是“上一个更炫的框架”，而是先把输入质量、检索质量、题型差异化和上下文管理做扎实。[来源：baseline p21-p25；提分教程 p7-p35]
- 对当前项目而言，最值得立即复用的不是向量 RAG、GraphRAG 或完整 Agent 框架，而是以下四类思想：
  - `解析质量优先`
  - `题型分流`
  - `结构化分块与结构字段增强`
  - `检索质量评估与自动回退`
- 动态记忆压缩、二次自检、Python 计算工具具备较高适配性，但应作为第二阶段增强能力，局部引入、避免全链路膨胀。
- 向量检索、重排序、GraphRAG、LightRAG、RAPTOR、smolagents 全框架替换等方案，当前更多适合作为研究储备而非近期主线。

## 7. 推荐的近期执行顺序

1. 修预处理与解析质量，建立结构化校验。
2. 升级 chunk 生成策略，补全 `section_path / clause_no / title` 等字段。
3. 做题型识别与差异化检索策略。
4. 加检索质量评估器和 baseline 回退。
5. 为多选题、计算题增加针对性验证。
6. 最后再试点动态压缩和受限 Python 计算。
