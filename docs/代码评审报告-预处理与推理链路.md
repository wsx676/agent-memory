## 二、影响正确性的设计风险（P1）

### P1-2. `_merge_reasoning_results` 存在"错误固化"

```148:150:api/services/retrieval_loop.py
    for result in new_results:
        if result.option not in merged or merged[result.option].verdict not in ("support", "refute"):
            merged[result.option] = result
```

一旦某选项在第 1 轮被判 `support/refute`，后续轮次**永不翻转**。若首轮因证据不全而误判，多轮补检索反而无法纠错。单调收敛的初衷是好的，但缺少"新证据显著更强时允许翻转"的例外。

建议：对已确认项，允许后续轮次在**新判读为确定性结论（support/refute）且置信度显著更高**时覆盖旧结论。置信度可从 reasoning 文本（`置信度XX%`）解析。

**状态：已修复**（见下方"修复记录"）。

### P1-3. evaluator 注释与实现不符

```89:91:api/services/retrieval_evaluator.py
    insuf_count = verdict_counts.get("insufficient", 0)
    answer_format = str(plan.get("answer_format", "single"))
    insuf_threshold = 1 if answer_format == "multi" else max(1, len(options) // 2)
```

注释写"单选/判断题 ≥2 个 insufficient 才 retry"，但判断题通常 2 个选项 → `max(1, 2//2)=1`，即 ≥1 就 retry，与注释矛盾，会让判断题过度重试。需对齐注释与实现（判断题是否要单独处理）。

**状态：已修复**（见下方"修复记录"）。

### P1-4. `enable_thinking=True` 与 `response_format=json_object` 组合需实测

```295:309:api/services/qwen_client.py
    extra_body: dict[str, object] = {"enable_thinking": enable_thinking}
    ...
```

`run.py` 对计算题/比较题强制 thinking。部分 Qwen 模型在 thinking 模式下与 `json_object` 强约束共用时，思考链可能挤占输出或触发接口报错。文档的 A/B 测试只比了 token/时延，未覆盖该兼容性。建议补一条"thinking+json_object 在目标模型上跑通"的验证。

## 三、可维护性 / 健壮性（P2，技术债跟进）

- **`reasoner.py` 用 `list[dict[str, object]]` 承载强类型数据**（`pending`），导致大量 `p["verdict"]` 隐式类型转换、可读性差。建议改用 `@dataclass`。
- **`OpenAI` client 每次调用新建**（`qwen_client.py:301`）。`run.py` 默认 8 并发 × 100 题 × 多轮 × 自检，重复建连接有开销，可模块级缓存。
- **异常大面积静默吞掉**（`qwen_client`、`main.py`、`run.py` 多处 `except Exception: pass`），线上排障困难，至少应记 warning 日志。
- **`_extract_numbers` 用 `\d+(?:\.\d+)?`** 会把"2024年"截成"2024"，年份与金额混淆，`numeric_boost` 可能被年份噪声误加分。建议数值匹配排除纯年份或结合单位。
- **`main.py:_write_answer_csv` 每题读全量+整体重写**（O(N²)），且 API 若并发调用存在 answer.csv 读写竞态。当前 `run.py` 走一次性 `write_submission_csv` 规避了，但 API 主链的这条路径仍有隐患。
- **magic number 密集**（reasoner 的 0.1/0.2/0.35、evaluator 的 0.72/0.5 等阈值散落各处），建议提为命名常量，便于调参与复现文档中的效果数据。
