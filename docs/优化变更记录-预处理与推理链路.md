## 三、阶段 2：全量重跑 + OCR 补齐

旧参数 `TARGET_MIN=300` 适配旧碎片产物（中位数 91 字），对新产物（中位数 295 字）几乎不触发合并。

PaddleOCR 3.7.0 在 Python 3.13 + Windows 环境下初始化失败（strides 属性类型错误）。改用 RapidOCR（ONNX CPU 推理）。

- 回退 PaddleOCR
- 自动检测引擎类型，适配不同返回格式

`requirements.txt` 新增 `rapidocr-onnxruntime==1.2.3`。

用 RapidOCR 对扫描版 PDF `csrc_0038_att2`（5 页纯图片）补跑 OCR，从 1 个 fallback 恢复为 5 个有效切片（2754 字）。

## 五、阶段 4：多步推理激活

### 5.1 问题诊断

对当前多步推理实现做深度诊断，发现系统设计了完整的 ReAct-lite 多轮架构，但**从未被激活**：

- 100 题 × 360 选项中 **0 个 insufficient**（全部 support/refute）
- 导致 evaluator 永远第一轮 accept（quality_score 几乎总是 >0.99）
- 多轮循环、memory ledger、query rewrite 形同虚设

根因在 `reasoner.py` 的 `_determine_verdict`：`avg_score < 0.15` 的阈值太低，`score_overlap` 余弦相似度即使不相关也容易超过。

### 5.2 P0：修复 reasoner 的 insufficient 判定

**新增辅助函数**：

```python
def _extract_option_markers(option: str) -> set[str]:
    """提取选项中的数值/百分号/金额等硬标记"""

def _check_evidence_substance(option: str, top_evidence_text: str) -> tuple[bool, float]:
    """检查 top 证据与选项的实质匹配度（标记命中率）"""
```

**三层 insufficient 检查**（`_determine_verdict`）：

| 层 | 条件 | 作用 |
|----|------|------|
| 绝对阈值 | avg_score < 0.2（从 0.15 提高） | 低质量证据判 insufficient |
| 实质匹配 | 选项含数值标记但 top-3 证据一个都没命中 | 证据和选项缺乏实质语义对应 |
| 相对置信度 | 选项分数 < 同题中位数的 35% | 某选项证据明显弱于其他选项（在 reason_options 中实现） |

`reason_options()` 重写为三阶段：逐选项独立判定 → 横向相对置信度比较 → 计算题特殊处理。

**效果**：insufficient 从 0 个 → 46 个（12%），25/100 题有 insufficient 选项。

### 5.3 P2：收紧 evaluator 的 accept 门槛

`retrieval_evaluator.py` 两处改动：

1. **多选题 insufficient 触发条件**：从 `>=2` 改为 `>=1`（多选错一个全错，不能放过）
2. **移除 quality=high 强制 accept 旁路**：有 failure_reasons 就 retry

```python
# 修改前
decision = "accept" if not failure_reasons or quality_label == "high" else "retry"

# 修改后
decision = "accept" if not failure_reasons else "retry"
```

**效果**：多轮触发从 0/100 → 39/100（8 题 2 轮 + 31 题 3 轮）。

### 5.4 P1：账本参与循环决策

重写 `retrieval_loop.py`，对齐"状态机 + 结构化 JSON 账本"方案。

**新增函数**：

```python
def _init_ledger(options) -> dict:
    """初始化跨轮账本：option_status / confirmed_results / confirmed_chunks / gaps"""

def _update_ledger(ledger, reasoning_results, evidence_map, candidate_chunks):
    """每轮结束后更新账本：固化已确认选项，提取缺口"""

def _build_gap_driven_plan(base_plan, ledger, options, evaluation):
    """根据 gaps 生成定向补检索计划——注入 insufficient 选项文本到 query_hints"""

def _merge_reasoning_results(confirmed, new_results, options):
    """合并推理结果：已确认的保留，只接受未确认选项的新结果（单调收敛）"""
```

**核心改动**（`run_retrieval_loop`）：

1. 循环前初始化 `ledger`
2. 每轮结束后 `_update_ledger` 更新状态
3. 第二轮起合并累积的已确认证据到候选 chunks
4. 第二轮起用 `_merge_reasoning_results` 合并结果（已确认选项不重算）
5. 下一轮 query 由 `_build_gap_driven_plan` 生成（gaps 驱动）
6. loop_logs 新增 `react_gaps` 和 `react_confirmed` 追踪

**验证（ins_a_011 为例）**：

```
第1轮: A=insufficient, B/C/D=refute → gaps=[A], confirmed=[B,C,D]
第2轮: query 注入选项A文本"众安白血病医疗险...", 补检索新证据
第3轮: 继续补检索
最终: B/C/D 保持 refute（不被覆盖），状态单调收敛
```
