# 大模型回答准确率优化方案

## 一、问题背景

当前系统在 fin_a（financial_reports）领域 20 题测试中的准确率：

| 版本 | 正确数 | 准确率 | 说明 |
|------|--------|--------|------|
| v3_1200cap（有hints） | 11/20 | 55% | 1200字符截断 + reasoning hints |
| v4_nohints（无hints） | 10/20 | 50% | 禁用hints后略降 |

9 道错题：fin_a_004, 008, 009, 011, 014, 016, 018, 019, 020

经独立作答验证，7/9 为纯 LLM 推理错误，2/9 部分召回缺失。禁用 reasoning hints 后准确率不升反降，说明 hints 的锚定效应是真实的但不是主要瓶颈。

---

## 二、原因分析

### A. 证据层面 — LLM 实际看到的证据可能不完整

#### A1. 1200字符截断可能丢失关键证据

`_EVIDENCE_SNIPPET_LEN=1200` 对每个 chunk 截断到 1200 字符。独立作答时读取的是完整 chunk，但 LLM 看到的是截断版本。

**典型场景**：
- fin_a_019：CATL 致股东信中"连续三年以净利润的50%实施现金分红"位于 Chunk 7 后半段，可能在 1200 字符之后
- fin_a_019：美的"自2019年起连续四年回购"位于 Chunk 2(p44) 后半段
- fin_a_004：研发费用占比等关键比率可能在表格行 1200 字符之后

**影响范围**：之前判定"召回充分但 LLM 推理错误"的 7 道题中，部分可能是截断导致证据丢失。

#### A2. 表格结构在格式化中残缺

`_format_evidence()` 对 table 类型保留换行但仍然截断 1200 字符。对于长表格（合并利润表、现金流量表等），1200 字符约容纳 15-20 行。关键数据行可能落在截断位置之后，导致 LLM 看到残缺表格——有表头和前几行，但缺关键数据行。

#### A3. 证据窗口的文档间竞争

配置：`_EVIDENCE_MIN_PER_DOC=5`、`_EVIDENCE_MAX_TOTAL=20`、`_EVIDENCE_MAX_TOTAL_CHARS=18000`

跨文档对比题（2个文档）场景：
- 每文档保底 5 chunk = 10 个，剩余 10 个 slot 按输入顺序填充
- 文档 A 的 chunks 排在前面时，文档 B 的关键 chunks 可能被挤出
- 两个长表格文档时，18000 字符安全阀可能过早触发

---

### B. 推理层面 — LLM 数值推理能力不足

#### B1. thinking_budget=1536 对复杂计算题不够

fin_a_004 类题目需要同时比较 4 个维度的两年数据（营收增速、现金流、研发占比、分红金额），每个维度需要：提取数字→计算→比较→判断。1536 tokens 约容纳 1000-1200 个中文字符的推理过程，4选项×2文档的多步推理可能捉襟见肘，导致后续选项推理草率收场。

#### B2. LLM 对金融数值的精确提取能力弱

从 9 道错题的独立分析中归纳的典型错误模式：

| 错误类型 | 案例 | 根因 |
|---------|------|------|
| 单位误读 | "每10股45.53元"→"每股45.53元" | 未注意"每10股"限定词 |
| 全年/末期混淆 | 美的全年43元→误认为38元（末期） | 未区分中期+末期=全年 |
| 数值近似错误 | 研发占比2.8%→误认为3.9% | 从表格中提取了错误的行或列 |
| 漏选正确项 | fin_a_004漏A、fin_a_009漏B | 多条件判断中遗漏某项 |

这些是 LLM 在长上下文+密集数字场景下的固有推理缺陷，非系统设计问题。

#### B3. 多选题"无法确认不选"的保守策略

当前 multi 题 prompt 明确写着"无法从证据中确认的不选"。证据充分时此策略正确，但证据被截断或不完整时，会导致本应选中的选项因"证据不足"被排除。

错题中漏选（缺正确选项）比多选（选了错误选项）更常见，与此策略直接相关。

---

### C. 系统层面 — 流程设计的副作用

#### C1. self-check 可能引入负面修正

所有 multi 题都触发 self-check（`needs_self_check()` 对 multi 题返回 True）。self-check 设计意图是纠正漏选/误选，但也可能把第一轮的正确答案改成错误答案。

self-check prompt 中包含"第一轮答案：{first_answer}"，产生**反向锚定效应**——LLM 倾向于在第一轮答案基础上微调，而非完全独立验证。第一轮答案恰好正确时，self-check 可能"过度纠正"导致变错。

当前结果文件未记录 self-check 前后答案差异，无法直接量化此影响。

#### C2. tf 题关闭 thinking 影响判断深度

`force_thinking=(answer_format != "tf")`——tf 题强制关闭 thinking。但 fin_a_018 等判断题需要验证多个条件（两家营收均双位数增长 + 宁德时代净利润增速>美的），需要数值提取和比较，关闭 thinking 后 LLM 凭直觉快速判断，容易出错。

fin_a_018 在两次测试中都答错（B 而非 A），与 thinking 被关闭有关。

#### C3. self-check 对 mcq 题覆盖不足

`needs_self_check()` 对 mcq 题仅在"无 support 信号"时触发。但：
- fin_a_015（mcq）在 v4_nohints 中从 A 变 D，说明 mcq 题输出本身有波动，却没有 self-check 兜底
- fin_a_008（mcq）两次都答错（D 而非 B），也未触发 self-check

---

### D. 检索层面 — BM25 的天然局限

#### D1. BM25 对表格数据检索效果差

表格 chunk 文本是数字密集的（如"423,701,834 362,012,554 17.04%"），关键词重合度低。题目问"研发费用占营业收入比重"时，BM25 能匹配到含"研发费用"的 chunk，但可能漏掉含具体百分比数字的表格行。

赛题明确**禁止使用向量模型和 rerank**，此限制对表格密集的 financial_reports 领域影响最大。本地 reasoner 的 `_supplement_numeric_chunks()` 能部分缓解（从选项提取数字补充检索），但仍基于精确数字匹配，无法处理近义数值场景。

## 三、优化方案（按优先级排序）

### P0：验证 1200 截断是否丢失关键证据

**目标**：确认"召回充分但 LLM 答错"的题目中，有多少是因为截断导致关键证据丢失。

**方法**：
1. 对 9 道错题，提取每题所有候选 chunk 的完整文本
2. 标注每个 chunk 中关键证据的字符位置（offset）
3. 对比 1200 字符截断后，关键证据是否被保留
4. 统计：关键证据在截断范围内的题数 vs 被截断的题数

**预期收益**：高——可能解释多道"召回充分但 LLM 答错"的题，并为后续截断策略调整提供数据支撑。

**实现难度**：低——写一个分析脚本即可，不涉及代码修改。

---

### P1：对比 self-check 前后答案变化

**目标**：量化 self-check 的正面/负面影响——修正了多少错误，引入了多少新错误。

**方法**：
1. 在 `eval_group_a_qwen.py` 中增加 `llm_before_selfcheck` 字段记录
2. 重跑 20 题，对比 self-check 前后答案
3. 统计：self-check 修正数 vs self-check 引入错误数 vs 无变化数

**预期收益**：高——直接量化 self-check 的净收益，决定是否调整触发条件。

**实现难度**：低——在评测脚本中加一行记录。

---

### P2：tf 题开启 thinking

**目标**：修复 fin_a_018 等判断题的推理深度不足问题。

**方法**：
```python
# qwen_client.py _call_qwen_api 调用处
force_thinking=True  # 统一开启，不再按题型区分
```

或更精细的方案：
```python
# run.py
THINKING_QUESTION_TYPES = {"calculation", "comparison", "tf"}  # 增加 tf
```

**预期收益**：中——fin_a_018 等判断题可能直接修复，但会增加 token 消耗和时延。

**实现难度**：极低——改一行代码。

**风险**：thinking 非确定性可能引入新的答案波动（参考 p2v9 一致率下降根因）。

---

### P3：增大 thinking_budget 到 2560

**目标**：为复杂多步推理题提供更充足的思考空间。

**方法**：
```python
# qwen_client.py _call_qwen_api
extra_body["thinking_budget"] = 2560  # 从 1536 提升
```

**预期收益**：中——多步推理题（fin_a_004 等）可能受益。

**实现难度**：极低——改一个参数。

**风险**：token 消耗增加约 40%，时延增加。需确认百炼 API 的 thinking_budget 上限。

---

### P4：multi 题 prompt 从"无法确认不选"改为"倾向选择"

**目标**：减少保守漏选。

**方法**：修改 `_build_multi_messages()` 中的 prompt 文案：
- 原："无法从证据中确认的不选"
- 改："对每个选项逐一判断，有支持证据则选，证据不明确但无明显反驳的也倾向选择"

**预期收益**：中——减少漏选，但可能增加误选。需要 A/B 测试验证净收益。

**实现难度**：低——改 prompt 文案。

---

### P5：增大截断长度到 1800 或按 chunk_type 差异化

**目标**：减少关键证据被截断的概率。

**方法**：
```python
# 方案A：统一提升
_EVIDENCE_SNIPPET_LEN = 1800
_EVIDENCE_TABLE_SNIPPET_LEN = 1800

# 方案B：table类型给更长截断
_EVIDENCE_SNIPPET_LEN = 1200       # prose 不变
_EVIDENCE_TABLE_SNIPPET_LEN = 2000 # table 提升到 2000
```

**预期收益**：中高——直接解决 A1 和 A2 的截断问题。

**实现难度**：低——改参数。

**风险**：总字符数增加，可能超过 LLM 上下文窗口。需同步调整 `_EVIDENCE_MAX_TOTAL` 或 `_EVIDENCE_MAX_TOTAL_CHARS`。

**前置条件**：P0 验证结果确认截断确实是问题后再实施。

---

### P6：self-check 触发条件精细化

**目标**：减少 self-check 的负面修正。

**方法**：修改 `needs_self_check()` 逻辑：
- multi 题：不再总是触发，改为"仅当选项数≤1 或全 insufficient 时触发"
- mcq 题：增加触发条件——"LLM reasoning 中含'不确定'/'可能'等低置信词时触发"
- tf 题：增加触发条件——"无 support 信号时触发"

**预期收益**：中——减少不必要的 self-check 调用（省 token），同时减少负面修正。

**实现难度**：中——需调整 `formatter.py` 逻辑并测试。

**前置条件**：P1 量化 self-check 净收益后再决定是否实施。

---

### P7：证据窗口分配优化

**目标**：解决跨文档对比题的证据窗口竞争问题。

**方法**：
- 对 comparison 题型（`detect_question_type() == "comparison"`），将每文档保底 chunk 数从 5 提升到 7
- 或按文档相关度动态分配 slot（而非固定保底+顺序填充）

**预期收益**：中——跨文档对比题的证据覆盖更均衡。

**实现难度**：中——需调整 `_format_evidence()` 的分配逻辑。

---

## 四、验证计划

### 第一轮验证（P0 + P1）

1. **P0 截断分析**：运行脚本分析 9 道错题的关键证据截断情况
2. **P1 self-check 对比**：修改评测脚本记录 self-check 前后答案，重跑 20 题

### 第二轮验证（基于第一轮结果）

- 若 P0 确认截断是主因 → 实施 P5（增大截断长度）
- 若 P1 确认 self-check 有负面影响 → 实施 P6（精细化触发条件）
- 始终实施 P2（tf 开启 thinking）+ P3（增大 thinking_budget）

### 评测方法

每项优化单独 A/B 测试，对比 v3_1200cap 基线（11/20=55%）：
- 正确数变化
- 变化题目明细（哪些题修复了，哪些题新出错了）
- token 消耗变化
- 平均时延变化
