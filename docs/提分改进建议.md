# 提分改进建议

## 1. 当前实现现状评估（基于代码核查）

> 以下评估基于对 `api/services/` 全部核心模块的逐行审查，结合赛题提分教程的完整要求。

### 1.1 各模块实现完整度

| 模块 | 完整度 | 核心证据 |
|------|--------|---------|
| PDF解析 | ~75% | PyMuPDF + pdfplumber + PaddleOCR 三路解析已通，但缺公式提取、多栏处理 |
| 规则化chunk检索 | ~85% | BM25 + 多字段加权 + 规则boost + CRAG质量门控 + 查询改写循环，最完整的模块 |

### 1.2 已实现的能力清单

- PyMuPDF 主解析器，pdfplumber 备选（含表格提取）
- PaddleOCR 扫描件处理（页面文本 < 40 字符时自动触发）

- 短段落合并（< 60 字符与 < 120 字符合并）
- 去重（前 160 字符去空后做 dedupe_key）

**规则化chunk检索（`retriever.py` + `retrieval_loop.py` + `retrieval_evaluator.py` + `planner.py`）**

- 多字段加权评分（title=4.0, section_path=3.0, clause_no=5.0, chunk_text=1.0）

- 文档级排序（`rank_documents`，top-3 聚合 + 信号覆盖 + 章节覆盖）
- chunk级排序 + 多样性去重（`_diversified_top_chunks`）
- 查询扩展（7组同义词、数字提取、条款引用提取、高价值术语提取）
- CRAG风格检索质量评估（8维评分：chunk数量/文档覆盖/章节覆盖/问题重叠/数字命中率/条款命中率/焦点术语命中率/选项判定覆盖）
- 检索循环（最多3轮，6种 query rewrite 策略：base/comparison_focus/numbers_focus/clause_focus/section_focus/option_split）
- 域感知过滤（insurance/regulatory/financial_reports/financial_contracts/research）
- 目录降权（`-6.0`）、短文本降权（`-1.5`）

**Qwen主链路推理（`qwen_client.py` + `reasoner.py` + `formatter.py`）**
- DashScope API 集成（OpenAI 兼容模式，`temperature=0`）
- 配置三项校验（`ENABLE_QWEN_LLM` / `DASHSCOPE_API_KEY` / `MODEL_NAME`）
- 本地预推理（`reason_options`，逐选项 overlap 评分 + 否定词检测）
- 证据格式化（含 doc/page/clause/section 定位信息）
- JSON 输出解析（支持 fenced code block 和 raw 两种格式）
- 答案归一化（single 取首字母 / multi 排序去重 / judge 单字母）
- Token 统计（prompt_tokens / completion_tokens / total_tokens）
- 答案格式约束输出（`answer.csv` + `evidence.json`，`formatter.py` 去重取 top-8）

### 1.3 关键差距对照（赛题要求 vs 当前实现）

> **赛题约束**：经向赛题方确认，Embedding 模型和 Rerank 模型不允许在正式提交中使用，仅允许使用 Qwen 系列模型 API。因此向量检索、混合检索、HyDE、Rerank 精排等依赖外部模型的能力均不在可选范围内，下表不再将其列为差距。

| 赛题提分教程要求 | 当前实现状态 | 差距说明 |
|----------------|------------|---------|
| 公式提取与 LaTeX 化 | ❌ 未实现 | 保险精算公式、财务比率公式会丢失结构 |
| 多栏布局阅读顺序恢复 | ❌ 未实现 | 研报和合同多栏排版可能乱序 |
| 多粒度分块（子块检索+父块回答） | ❌ 未实现 | 仅单一粒度分块 |
| Bash/Python 代码执行工具 | ❌ 未实现 | 计算题完全依赖 LLM 文本推理，易出错 |
| 答案自检/验证机制 | ❌ 未实现 | 无第二轮验证 |
| 动态记忆压缩（分层存储+选择性遗忘+渐进压缩） | ❌ 基本未实现 | 仅 `memory.py` 26行简单 fact 汇总 |
| 结构化事实提取（公式/数值/条件判断） | ❌ 未实现 | |
| Token 全局预算管理 | ⚠️ 部分 | 有单题统计，无全局预算控制 |

**赛题约束下的检索策略定位**：由于不能使用向量模型和 Rerank，当前 BM25 + 多字段加权 + 规则 boost + CRAG 质量门控的纯词法检索方案已是赛题允许范围内的合理选择。后续检索层优化应聚焦于分词精度、规则 boost 调参和查询改写，而非引入向量检索或 Rerank。

## 2. 当前分数判断与核心瓶颈

当前总分仅 `25/100`，结合比赛评分公式与项目现状，可以判断核心瓶颈仍然是准确率，而不是 `token`。

- 评分公式中，准确率权重为 `70%`，`token` 效率权重为 `30%`
- 如果准确率不足，即使 `token` 很省，总分也很难显著提升
- 当前阶段最重要的目标不是先继续压缩 `token`，而是优先提升答题正确率与输出稳定性

结合代码核查结果，当前系统**已有较好的检索基础设施**（BM25 + 规则boost + CRAG循环），真正拖分的关键点集中在：

1. **证据输入量不足** — Qwen 原仅看到 6 chunk × 220 字符（已优化为 10 × 600），chunk_text 存储截断 1200 字符仍限制长段落信息
2. **推理层过于简化** — reasoner 仅做 overlap + 否定词，无法胜任计算/对比/条款定位题
3. **无计算能力** — 赛题中大量公式计算题完全依赖 LLM 文本推理
4. **多选题风险** — 可能输出 `N/A`，缺少逐选项稳定判定流程
5. **动态记忆压缩缺失** — 赛题名称核心能力基本空白，长文档场景下 token 效率低

> **赛题约束提醒**：赛题明确禁止使用 Embedding 模型和 Rerank 模型，仅允许 Qwen 系列模型 API。因此检索层只能在词法检索（BM25 + 规则）框架内优化，不能依赖向量检索或 Rerank 精排。

## 3. 代码级问题清单（需立即修复）

### 3.1 Qwen 证据输入量不足（已部分修复）

**已完成的优化**（`qwen_client.py` `_format_evidence`）：
- chunk 数量：`chunks[:6]` → `chunks[:10]` ✅
- 单片段长度：`[:220]` → `[:600]` ✅

**仍存在的问题**：`preprocess.py` L576 的 `chunkText=part[:1200]` 将每个 chunk 存储时截断为 1200 字符。已有 chunk 数据中仅 1.5%（888/61158）的 chunk 达到此上限，但对这些信息密集的长段落（条款原文、表格数据），1200 字符仍可能丢失后半部分。

**建议**：后续重新预处理时将截断阈值提升至 2000 字符，或按 chunk_type 动态调整（clause 类型不截断，prose 类型截断 2000）。当前已有 chunk 无需重新生成即可受益于已完成的 Qwen 端优化。

### 3.2 Qwen max_tokens 过低

`qwen_client.py` L192 中 `max_tokens=256`，对多选题的逐选项推理可能不够。复杂多选题需要 4 个选项逐一分析，256 token 容易截断推理过程。

**建议**：提升至 512-768，或按题型动态设定（multi=768, single=384, judge=384）。

### 3.3 reasoner 否定词检测过于粗糙

`reasoner.py` L7 的 `NEGATIVE_HINTS = ("不", "未", "不得", "无", "除外")` 仅做子串匹配。 "不适用" 和 "不适用的除外" 会被同等对待，导致 verdict 误判。

**建议**：引入否定词的上下文窗口（前后 20 字符），区分 "不承担" 和 "不适用...的除外"。

### 3.4 formatter 的 choose_answer 兜底逻辑风险

`formatter.py` L15 中，当所有选项均为 `insufficient` 时，返回第一个 insufficient 选项。对多选题这意味着只输出单个字母，可能直接零分。

**建议**：多选题在全部 insufficient 时，应回退到 Qwen 的整体判断而非本地规则。

### 4.3 P2：推理层核心改造

#### 4.3.1 将简单 overlap 规则升级为逐选项验证

当前 `reasoner.py` 仅依赖 overlap + 否定词，对以下题型明显不足：
- 多选题（需逐项独立判定）
- 判断题中的例外条款
- 跨文档对比题
- 计算题
- 排序题

建议改造为"逐选项验证器"：
- 每个选项单独判断 `support / refute / insufficient`
- 对每个选项绑定 top-3 对应证据片段
- 对多选题逐项验证后合并结果
- 对 `insufficient` 选项触发补充检索或保守判定

#### 4.3.2 增加轻量计算器（Bash/Python 代码执行）

这是赛题提分教程第七章强烈建议的方案，对计算题收益极高。

**实现方案**：
- 在 Qwen 的 tools 定义中加入 `execute_python(code: str)` 工具
- 模型输出 Python 代码 → 沙箱执行 → 返回 stdout → 模型判断选项
- 代码执行超时设为 5 秒，禁止 import os/subprocess
- 适用场景：保险退保金计算、身故保险金排序、财务指标增长率计算

**备选方案（更轻量）**：
- 预处理阶段提取数值和公式，构建结构化 facts
- 推理阶段用 Python 规则引擎直接代入计算
- 不需要 LLM 生成代码，但覆盖面有限

#### 4.3.3 多选题专项治理

- 多选题必须走逐选项验证链路，禁止一次性整体判断
- 若某些选项为 `insufficient`，触发补充检索（当前 retrieval_loop 已支持，但需确认多选题确实进入循环）
- 禁止输出 `N/A`：最差情况输出所有 `support` 或 `insufficient` 选项
- 输出前统一做：合法字母抽取 → 去重 → 排序
- 多选题只选出 1 个选项时触发轻量自检

#### 4.3.4 低置信题轻量自检

不建议全量开启 CoT 或自检，仅对以下情况触发二次确认：
- 多个选项均为 `insufficient`
- 计算题缺数字
- 多选题只选出 1 个选项
- 跨文档题证据覆盖不足
- 输出答案与证据显著矛盾

自检方式：将第一轮答案 + 证据 + 题目重新给 Qwen，要求验证每个选项的判定是否正确。

- 加强金额、比例、年份、条款号的 exact boost（当前已有，可调参增强）
- 对长文档引入章节级粗排 + chunk 级细排（当前 rank_documents + rank_chunks 已有雏形，可强化两阶段衔接）
- 调整 `TOP_K_CHUNKS = 12` → 15-18，增加召回量

#### 4.4.2 上下文组装优化

检索到的片段进入 prompt 前做：
- 去重（当前已有 dedupe_key）
- 邻近段落合并（同一页码的相邻 chunk 合并）
- 边界修复（被截断的条款补全首尾）
- 信息密度排序（含数字/条款号的片段优先）

按领域差异化组装：
- `insurance / regulatory / financial_contracts`：章节级、条款级组装
- `financial_reports / research`：表格字段级、指标级组装

### 4.5 P4：动态记忆压缩（务实版）

> 赛题名称即"动态记忆压缩"，当前基本缺失。但不宜一步到位建重型系统，建议分两步走。

#### 4.5.1 第一步：结构化 facts cache（与 P2 同步推进）

在预处理阶段，从 chunk 中提取结构化事实，按领域缓存：

- `insurance`：等待期天数、免责条件列表、免赔额、给付规则、现金价值公式
- `financial_reports`：营收、净利润、研发投入、现金流、分红（含年份和数值）
- `regulatory`：条款号、时限（天数/工作日）、主体义务、例外条件
- `financial_contracts`：发行规模、票息、评级、偿付顺序、特殊条款
- `research`：市场规模、同比增长率、预测值、机构观点

这些 facts 比纯文本更稳定，比完整知识图谱更轻，能显著帮助跨文档聚合和计算题。

#### 4.5.2 第二步：单题推理内的渐进压缩

参考赛题提分教程第四章，在单题推理链内部实现：

1. **分段读取**：长文档按章节分段，每读一段提取关键信息（公式、数值、条件判断）
2. **压缩替代**：只保留提取结果进入下一段，丢弃原始文本
3. **结构化摘要**：用模板格式存储（`[CONTEXT SUMMARY]` + Goal + Key Formulas + Numerical Values + Pending Verification）
4. **Memento 模式**：题目原文、精确数值、例外条件条款不压缩，始终保留原文
5. **触发策略**：当 prompt tokens ≥ 模型上下文窗口 × 0.7 时触发压缩

这套方案不需要跨 session 记忆，只在单题推理内部工作，复杂度可控。

## 5. Prompt 设计优化

### 5.1 领域特化 Prompt

当前 `qwen_client._build_messages` 使用单一 system prompt 处理全部领域。建议按领域拆分：

- `insurance`：强调等待期、免责、给付、免赔额、现金价值，要求先定位条款再判断
- `regulatory`：强调条款适用、例外（"但书"）、时限、主体责任，要求引用条款原文
- `financial_contracts`：强调发行条款、评级、发行规模、违约条款，要求区分主体评级和债项评级
- `financial_reports`：强调表格字段、同比口径、财务指标一致性，要求标注年份
- `research`：强调年份、预测值、市场规模、机构观点，要求区分事实和观点

### 5.2 按题型拆 Prompt

- `single / judge`：直接输出字母
- `multi`：要求逐项核对再输出排序字母，明确提示"漏选不得分"
- `calculation`：要求先抽公式与数字，再代入计算，再输出最终选项
- `comparison`：要求统一字段口径后再比较，逐文档列出数据

### 5.3 Few-shot 示例

在 prompt 中提供 1-2 个已答对的题目作为示例，帮助模型理解答题格式和推理过程。注意示例不要占用过多 token（每个示例控制在 200 token 以内）。

## 6. 不建议优先做的事

当前阶段（25分）不建议优先投入以下方向：

| 方向 | 不建议原因 |
|------|-----------|
| 向量检索 / Embedding 模型 | **赛题明确禁止**使用 Embedding 模型，仅允许 Qwen 系列模型 API |
| Rerank 模型（Cross-Encoder 等） | **赛题明确禁止**使用 Rerank 模型，仅能靠 BM25 + 规则 boost 做排序 |
| HyDE（假设答案检索） | 依赖 Embedding 模型生成假设文档向量，赛题禁止 |
| 重型长期记忆系统（GraphRAG / LightRAG） | 预处理 Token 消耗大，当前准确率瓶颈不在跨文档推理结构 |
| 跨 session 用户记忆 | 本赛题是单题独立推理，无跨题关联 |
| 复杂 Function Calling / 多工具调度 | Token 消耗增加约 18%，当前更需稳定而非灵活 |
| 全量 CoT | 每题都做 CoT 会大幅增加 Token，收益不明确 |
| 过度复杂的双检索器融合 | 增加架构复杂度但收益不确定 |

## 8. 最终结论

从当前 25 分继续往上提，最有效的路径分三个阶段：

**第一阶段（P0-P1）**：把基础做对 — 修代码缺陷、确认主链、修预处理断链。这些是"不应该丢的分"，修复后预计可稳定在 30-35 分。

**第二阶段（P2）**：把复杂题做对 — 逐选项验证 + 计算器 + 多选题专项。这是最大的提分空间，计算题和多选题从随机猜到稳定得分，预计可到 40-50 分。

> **P2 进展（已完成）**：逐选项验证器、多选题专项、低置信自检、prompt改进、API健壮性增强均已完成。关键修复：`enable_thinking:false`关闭Qwen3思考模式，消除非确定性失败。100题测试LLM成功率**100%**，延迟降至3.2s/题。轻量计算器待实现。

**第三阶段（P3-P4）**：把效率做高 — 上下文优化 + 领域 Prompt + 动态记忆压缩。在准确率提升后，通过压缩和优化提升 Token 效率分，预计可到 50-60 分。

如果只选三个最该优先动手的点：

1. **修复代码缺陷 + 确认 Qwen 主链稳定运行**（P0）
2. **修复 PDF/chunk 质量与断链问题**（P1）
3. **重写推理流程：逐选项验证 + 轻量计算器 + 多选题专项**（P2）

这三项最有希望在当前分数基础上带来最明显、最可验证的提分效果。
