## 一、当前项目架构现状（评估前提）

评估优化方案前，必须先明确当前代码的实际架构，因为多篇文档基于**旧架构假设**提出方案，
部分假设已不成立。

### 1.1 当前实际架构

```
题目 → 检索层(BM25+规则增强) → reasoner规则预判 → Qwen主判 → self-check自检 → 最终答案
```

| 层级 | 当前实现 | 关键状态 |
|---|---|---|
| 检索层 | BM25 + 条款编号加权 + 数值专项补检索 + 多轮gap-driven补检索 | 已较完善 |
| reasoner | 多信号打分 + 否定词检测 + 实质匹配检查 | **reasoning_hints 已完全禁用** |
| Qwen主判 | 分题型prompt（single/multi/judge）+ thinking_budget=2560 | 核心判定层 |
| self-check | 所有multi题触发 + mcq/tf无support时触发 | 证据溯源自检 |
| 合并层 | **无 refute_veto / 无 P0 merge** | Qwen答案直接作为最终答案 |

### 1.2 关键架构变化（与文档假设的差异）

**轨迹分析优化方案的核心假设已失效**：

该方案假设"修好 reasoner 就能通过**现有合并机制**（refute_veto / P0 merge）自动纠错"。
但当前代码中：

- [run.py](run.py) 第 140 行：`final_answer = qwen_result.answer` —— Qwen 答案直接作为最终答案
- [qwen_client.py](api/services/qwen_client.py) 第 308-309 行：`reasoning_hints = []` —— reasoner 预判已被完全禁用
- [formatter.py](api/services/formatter.py) 中只有 `choose_answer`（规则兜底）和 `needs_self_check`，**没有 refute_veto 和 P0 merge**

这意味着：**修好 reasoner 的语义判断能力，不会通过合并机制传递到最终答案**。
reasoner 当前仅影响"是否触发多轮补检索"（通过 insufficient 判定），不直接影响 Qwen 的答案。

## 三、方案适用性评估

### 3.1 适合做的方案（推荐）

#### ✅ P0：七维验证框架 + strictness 参数（reg优化2 + reg优化3）

**优先级：最高。这是当前阶段最值得做的方案。**

**适合原因**：
1. **完全符合当前架构方向**：当前架构已是"Qwen 主判"，七维框架正是把语义判断系统化地交给 Qwen，而非依赖规则枚举
2. **解决根本问题**：当前 prompt 缺乏结构化检查清单，Qwen 容易遗漏检查维度（如方向矛盾、符号相反、来源角色）
3. **strictness 解决域间冲突**：research 域过度选择、regulatory 域过度剔除的相反失败模式，用 strictness 变量注入比写多套 prompt 更干净
4. **可持续维护**：新错误类型出现不需要加规则，框架天然覆盖
5. **B 榜泛化**：七维通用，新领域只需分配 strictness 值

**实施建议**：
- 改 [qwen_client.py](api/services/qwen_client.py) 的 system prompt，将七维检查清单注入
- 在 `_build_messages` 中按 domain 注入 strictness 变量
- strictness 映射：research/财报 → high，regulatory → inclusive，保险/合同 → balanced
- **不改 reasoner 和 run.py 的合并逻辑**，只改 prompt 层

**预期收益**：覆盖全部已知错题根因（方向矛盾、符号相反、实体混淆、来源角色误判等），预计提升 3-5 分

**风险**：低。只改 prompt 文本，不改代码逻辑，可通过 20 题哨兵验证快速回归

---

#### ✅ P1：Qwen prompt 方向性检查指令（轨迹分析修复5）

**优先级：高。可作为七维框架的先导版本快速上线。**

**适合原因**：
1. 直接改进 Qwen 的 prompt，符合当前架构
2. 方向性检查（增长/微降、+3.6%/-3.6%、显著增长/先升后降）是 research 域的核心错误模式
3. 实施成本极低（15 分钟改 prompt 文本）

**可改进点**：
- 不要写成"打补丁"式具体词对（增长/微降），而应抽象为"方向/趋势一致性检查"原则
- 如果已上七维框架，此方案被维度3（方向/趋势对齐）完全覆盖，无需单独做
- **建议**：如果时间紧先上此方案，时间充裕则直接上七维框架

---

#### ✅ P2：_check_evidence_substance 量级词检查（轨迹分析修复4，改进版）

**优先级：中。影响多轮补检索触发，有实际价值。**

**适合原因**：
1. reasoner 虽然不直接影响最终答案，但其 insufficient 判定会**激活多轮补检索**（见 [retrieval_loop.py](api/services/retrieval_loop.py) 的 gap-driven 机制）
2. 当前 [_check_evidence_substance](api/services/reasoner.py#L89) 已存在，但缺乏"千亿/百亿"等量级词检查，导致 020-C 这类"核心数值未出现"的选项未被判定为 insufficient，从而不触发补检索
3. 改进后能让检索层更积极地补检索缺失证据

**可改进点**：
- 不要只加"千亿/百亿"，应抽象为"选项核心数值标记必须在证据中出现"的通用规则
- 量级词提取应排除年份等弱标记（如"2025"不应作为核心数值标记）
- 与七维框架的维度2（数值对齐）配合，reasoner 做存在性检查，Qwen 做语义判断

---

#### ✅ P3：页型感知分块管线（chunk细分方案 + 评审修正）

**优先级：中。B 榜优先的系统性优化，解决证据质量问题。**

**适合原因**：
1. **解决真实问题**：目录页（ev5/ev7）和封面页（020-C）被误召回为证据，当前完全没有页型分类
2. **当前 [StructuredChunk](api/models.py#L68-L78) 已有 `chunk_type` 字段**（区分 table/prose/clause），扩展 `page_type` 字段是自然演进
3. **"标记不删除"策略优于预处理时删除**：目录页在 B 榜文档级召回中仍有价值，检索层降权比物理删除更灵活
4. **正文按段落/句号切分优于固定字数硬切**：当前 [postprocess_chunks.py](scripts/postprocess_chunks.py) 只做小chunk合并，不按语义边界切分
5. **评审的修正意见质量很高**，特别是特征打分替代单条件判断、双索引、三级切分

**必须吸取的教训**：
- 项目此前有 `_looks_like_toc` 函数，因正则误判导致**图表页整页丢失**，已被完全禁用
- 新的目录页检测**必须用特征打分**（评审建议的 `toc_score`），不能用单条件判断
- **必须引入 `toc_candidate` 中间类型**，降低误判带来的损失

**实施建议（采纳评审修正后）**：
1. **页型分类器**：用特征打分（点引导线+编号标题+图表索引+短行占比），分级判定 toc/toc_candidate/body
2. **图表页判定更严格**：不能仅靠数字行占比（会误伤财务报表），需同时满足图表标题+低句子比例+无表格结构
3. **正文三级切分**：语义单元（段落/条款）优先 → 句子合并 → 硬切兜底，target=450/max=700
4. **双索引**：evidence index（排除 toc/cover）+ document index（toc 低权参与）
5. **检索层类型权重做成配置**，不硬编码，按题型/领域感知
6. **find_tables 分阶段接入**：先在已知出错文档验证，再推广

**风险**：中。需要重新跑全量预处理 + 扩展 StructuredChunk 模型 + 改检索层，影响面广

**关键约束**：不适合 A 榜冲刺期做（需重跑全量预处理），应放在 B 榜前

---

#### ✅ P4：评估指标体系（chunk细分方案评审新增）

**优先级：中低。与 P3 配套，验证 chunk 优化效果。**

**适合原因**：
1. chunk优化是系统性收益，只看最终准确率不够——可能偶然改变答案
2. 评审提出的6个指标（目录污染率/证据召回率/证据纯度/字段覆盖率/截断损失率/误杀率）能精确度量优化效果
3. 特别"误杀率"指标可以防止重蹈 `_looks_like_toc` 误删正文覆辙

**实施建议**：与 P3 同步建立，作为 P3 各阶段的验证门槛

### 3.2 不适合做或需改进的方案

#### ❌ 轨迹分析修复1（反义词表扩展 + 符号保留）

**不适合原因**：
1. **架构假设已失效**：该方案假设修好 reasoner 的反义词检测和符号检测后，通过 refute_veto 自动纠错。但当前代码**没有 refute_veto**，reasoner 的 refute 判定不直接影响最终答案
2. **reasoning_hints 已禁用**：reasoner 的判定结果已不注入 Qwen prompt（因准确率仅 50%），修好反义词检测也无法传递
3. **打补丁不可持续**：每发现一个新反义词对就加一条，research 和 regulatory 的反义词需求还可能冲突

**改进方向**：方向性检查和符号检查应通过七维框架的维度2/维度3，由 Qwen 在 prompt 层完成，而非在 reasoner 规则层枚举

---

#### ❌ 轨迹分析修复2（needs_self_check 增加 Qwen-reasoner 冲突检测）

**不适合原因（当前形态）**：
1. 当前 [needs_self_check](api/services/formatter.py#L51) 已对所有 multi 题触发自检，mcq/tf 无 support 时也触发——覆盖面已经较广
2. 方案提出的"Qwen 选了 reasoner 判 insufficient 的选项时触发"——但 reasoning_hints 已禁用，reasoner 的 insufficient 判定对 Qwen 选择无直接影响
3. 增加此条件可能**过度触发自检**，增加 token 消耗而非提升准确率

**可改进方向**：如果启用七维框架的结构化输出（verdict 字段），可将自检触发条件改为"七维检查中任一维度标记为冲突但选项仍被选中"——这才是有意义的冲突检测

---

#### ❌ 轨迹分析修复3（否定词上下文检查——区分方法论剔除）

**不适合原因**：
1. 同修复1，reasoner 的否定词检测结果不直接影响最终答案
2. 否定词作用域收窄是 regulatory 域的特定需求，做成全局规则可能影响其他域
3. 方法论词（剔除/扣除）与否定词的区分逻辑复杂，匆忙上线容易引入退化

**改进方向**：由七维框架的维度4（逻辑结构对齐）和维度6（来源/角色对齐）在 Qwen 层处理，而非 reasoner 规则层

---

#### ⚠️ reg优化1（按 domain 路由隔离 prompt）——需改进

**不适合当前形态，但思路有价值**：

1. **"为每个 domain 写完整 prompt"会回到打补丁老路**——每加一个新错误类型就得想"属于哪套、改哪个 prompt"
2. **思路正确的部分**：research 和 regulatory 的失败模式相反，必须隔离处理——这一点是对的
3. **更好的实现方式**：用七维框架 + strictness 变量注入（reg优化3），而非三套独立 prompt

**结论**：reg优化1 的"domain 路由"思路被 reg优化2/3 的"统一框架 + 变量注入"方案吸收和替代

---

#### ⚠️ reg优化4（十维扩展）——暂不适合，B 榜前再评估

**不适合当前阶段**：

1. **7 维已覆盖全部已知错题**：文档自己确认"已知错题不需要新维度"
2. **超过 9 维会稀释 Qwen 注意力**：文档自己指出此风险
3. **3 个新维度（时序/例外但书/条件完整性）是 B 榜防御**：A 榜阶段无已知错题需要它们
4. **增量复杂度**：10 维 prompt 更长，Qwen 输出更多，验证成本更高

**建议**：A 榜先上 7 维 + strictness，B 榜前用一天时间评估 3 个新维度是否需要

### 3.3 上下文管理层方案（来自 analysis 提分教程第4章 + Baseline教程）

> 赛题名称"动态记忆压缩"的直接对应。当前项目完全没有动态记忆压缩机制，
> 证据组装采用"检索→一次性组装→单轮Qwen调用"的静态流程。
> 评分公式：准确率占 70%，Token 效率占 30%，优先做"既提准确率又省 token"的方法。

#### ✅ P6：结构化摘要模板（Hermes 格式）

**优先级：高。零流程改动，直接提升证据组装质量。**

1. 当前 [_format_evidence](api/services/qwen_client.py) 用 plain text 拼接证据，缺乏结构化字段标注
2. Hermes 模板：`[CONTEXT SUMMARY] + Goal + Documents Read + Key Formulas + Numerical Values + Pending Verification`
3. 按题型选字段：计算题突出 Key Formulas + Numerical Values，条款题突出 Exception Conditions
4. **不改流程，只改证据组装格式**，Key Formulas 和 Numerical Values 不会被 LLM 总结语言改写导致精度丢失
5. 预期收益：Qwen 对关键信息定位准确率提升，间接 +1-2 分。风险：极低

#### ✅ P7：信息密度控制扩展（保险公式段/监管例外段 boost）

**优先级：高。扩展现有 _PRIORITY_SECTIONS，实施成本极低。**

1. 当前 [_PRIORITY_SECTIONS](api/services/qwen_client.py) 只覆盖财报域（利润分配/分红/营收/净利润）
2. 扩展到全 5 域：保险（现金价值/退保费用/身故保险金/等待期/责任免除）、监管（除外/但书/不适用/特别决议/普通决议）、合同（回售/赎回/交叉违约/增信）、研报（复合增速/市场规模/CR4）
3. 同时定义 _DEPRIORITIZE_SECTIONS（释义/投保须知/本合同构成等模板文本降权）
4. 预期收益：关键段落命中率 +5-10%，间接 +1-2 分。风险：低

#### ✅ P8：Bash 工具 / Python 代码执行（消灭计算题算术错误）

**优先级：高。直接解决公式计算题的 LLM 计算短板。**

1. 公式计算题（ins_a_001/002/003、fin_a_001 等）算术完全依赖 Qwen 文本推理，多步运算易错
2. 50 token Python 代码 vs 200+ token CoT 推理，既提准确率又省 token
3. 流程：LLM 生成代码 → Bash 沙箱执行 → 拿精确结果 → 语义判断
4. 跨文档数值对比题可一次提取多文档数据再统一计算
5. **注意**：当前 no-tool 模式引入工具会增加约 18% prompt token（Baseline 数据），但计算题准确率提升可覆盖
6. 仅对计算题/跨文档数值对比题启用，事实查找题不需要
7. 预期收益：计算题 +3-5 分，同时省 completion token。风险：中（需设计沙箱）

#### ✅ P9：CoT 按需开启（简单题关 thinking 省 token）

**优先级：中。直接降低 token 消耗，不影响准确率。**

1. 当前 [run.py](run.py) 对**全题型开启 thinking**（thinking_budget=2560），Baseline 教程建议"按需开启，非必要不开"
2. 简单事实查找题（res 域 mcq/tf）不需要推理链，直接输出答案即可
3. Baseline 实测：CoT 使 completion token 从 15 万涨到 100 万+
4. 建议：计算题/multi题/跨文档对比题 → 开 thinking；简单事实查找题 → 关 thinking
5. 预期收益：completion token 降低 30-50%。风险：低

#### ✅ P10：CRAG 三级处理补 INCORRECT 兜底

**优先级：中。当前已有 AMBIGUOUS 级，补全三级处理。**

1. 当前 [retrieval_loop.py](api/services/retrieval_loop.py) 的 gap-driven 补检索 ≈ CRAG 的 AMBIGUOUS 级
2. 缺少 INCORRECT 级兜底——检索质量极差时应回退硬截断全文阅读
3. CRAG 关键洞察：检索质量评估用关键词重叠度+语义一致性等轻量特征即可
4. 评分 ≥0.7 直接用 / 0.3-0.7 补检索 / ≤0.3 回退硬截断
5. 预期收益：减少检索完全失败时的错误（约 2-3 道）。风险：低

#### ⚠️ P11：动态截断 + 渐进压缩（Claude Code 4层）

**优先级：中低。系统性优化但改动面大，适合 B 榜。**

1. 当前无"分段读取→压缩→继续读"循环，是赛题核心挑战的最大差距
2. Claude Code 4 层渐进：Snip（免费截断）→ Microcompact → Context Collapse → Autocompact（LLM 摘要），80% 场景 Snip 就够
3. Memento 保留策略：精确数值/例外条件不压缩
4. 触发策略：prompt tokens >= 上下文窗口 × 0.7
5. **难点**：需把单轮调用改为多轮循环，架构改动大；过度压缩可能丢失关键条件
6. 建议先上 Snip 层（免费），再上 Memento 保留，最后才考虑 LLM 摘要。风险：高

#### ⚠️ P12：LightRAG 跨文档知识图谱

**优先级：低。预处理成本高，适合 B 榜跨文档题专项。**

1. 跨文档对比题（fin_a_001/005）和多文档联合推理题（ins_a_001/003/005）是薄弱环节
2. LightRAG 双向量索引（实体+关系）比 GraphRAG 社区检测更轻量，支持增量更新
3. **难点**：预处理需大量 LLM 调用做实体抽取；当前禁用向量模型需替代方案；赛题方计算预处理 token
4. 风险：高

#### ❌ 不适合当前阶段的方法

| 方法 | 不适合原因 |
|---|---|
| MemGPT 虚拟内存管理 | 为"短文档+长对话"设计，本赛题是"长文档+短推理"，换页逻辑需大幅改造 |
| GraphRAG 全量版 | 社区检测+逐社区摘要开销大，LightRAG 更轻量 |
| RAPTOR 树状递归摘要 | 依赖向量模型做 embedding，当前禁用 |
| HyDE 假设文档检索 | 依赖向量检索，当前禁用；变体收益不确定 |
| smolagents Code Agent | 需引入新框架，Bash 工具（P8）已覆盖计算需求 |
| Kimi Code 6级优先级 | 面向长对话任务状态管理，本赛题单题推理不需要 |

## 六、核心结论

### 推理层优化（前5篇文档）

1. **轨迹分析优化方案（5个修复）的核心假设已失效**：当前架构中 reasoner 不直接影响最终答案（reasoning_hints 已禁用，无 refute_veto/P0 merge），修 reasoner 的语义判断能力无法传递到答案层。只有影响"补检索触发"的改进（修复4）仍有价值。

2. **七维验证框架（reg优化2+3）是最符合当前架构的方案**：把语义判断系统化地交给 Qwen，用 strictness 变量解决域间冲突，可持续维护且 B 榜可泛化。

3. **reg优化1 的 domain 路由思路被七维框架 + strictness 吸收**：不需要写三套独立 prompt。

4. **reg优化4 的十维扩展是 B 榜防御**：A 榜阶段 7 维已足够，过早扩展反而稀释 Qwen 注意力。

### 预处理层优化（chunk细分2篇文档）

5. **页型感知分块管线方向正确，但必须采纳评审修正**：原方案的目录页单条件判定、图表页数字占比判定、固定字数硬切、table统一加权等做法有误伤风险，评审的特征打分+双索引+三级切分+领域感知权重是更稳妥的实现。

6. **必须吸取 `_looks_like_toc` 误判教训**：项目此前因目录页正则误判导致图表页整页丢失，新的页型分类器必须用特征打分+`toc_candidate`中间类型，且必须用"误杀率"指标验证有效正文未被误删。

7. **chunk优化是B榜级任务**：需要重跑全量预处理+扩展模型+改检索层，不适合A榜冲刺。应放在推理层优化（P0七维框架）上线后、B榜开始前实施。

### 总体原则

8. **推理层和预处理层优化互补且有序**：推理层优化（改prompt）成本低、见效快，应优先做；预处理层优化（重跑chunk）成本高、系统收益，B榜前做。两者不冲突——证据质量提升后，七维框架的判断也会更准。

9. **所有方案的共同原则**：不要在规则层打补丁做语义判断（无论是 reasoner 还是预处理层的正则），而要在 Qwen prompt 层用结构化框架系统化检查，在预处理层用特征打分而非单条件判定。规则层只做它擅长的存在性检查和页型标记，语义判断完全交给模型。

### 上下文管理层优化（analysis 2份教程）

10. **当前项目与赛题核心挑战的最大差距是动态记忆压缩**：赛题名称直接点名"动态记忆压缩"，但当前项目完全没有"分段读取→压缩→继续读"的循环，证据组装是静态一次性拼接。这是 B 榜需要系统性解决的差距。

11. **最高性价比的上下文管理改进是 P6/P7/P9**：结构化摘要模板（改格式零流程改动）、信息密度控制扩展（改配置）、CoT 按需开启（改参数），三者实施成本极低且"既提准确率又省 token"。

12. **Bash 工具（P8）是计算题的根治方案**：50 token 代码 vs 200+ token CoT 推理，既消灭算术错误又省 token。但需注意 no-tool → FC 模式会增加约 18% prompt token，仅对计算题启用可覆盖成本。

13. **动态截断+渐进压缩（P11）是 B 榜系统级任务**：Claude Code 的 4 层渐进压缩（Snip→Microcompact→Context Collapse→Autocompact）给了成本可控的方案——80% 场景 Snip（免费截断）就够。但需要把单轮调用改为多轮循环，架构改动大，应放在推理层和预处理层优化上线后实施。

14. **MemGPT/GraphRAG/RAPTOR/HyDE 不适合当前阶段**：MemGPT 为"短文档+长对话"设计而非本赛题的"长文档+短推理"；GraphRAG/RAPTOR/HyDE 依赖向量模型或预处理成本过高。LightRAG 是更轻量的图谱替代，但也应放在 B 榜跨文档题专项优化时评估。
